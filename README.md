# K-D Agent：任务卡驱动的双模型 Multi-Agent 协作系统

> **贵模型只做规划与验收，便宜模型承担全部高频执行；任务状态以 Markdown 任务卡落盘，
> 依赖感知并行调度，全程可审计、可计量、可复现。**
>
> 架构师 = Kimi K3（长上下文 + 多模态，订阅端点）
> 工程师 = DeepSeek V4-Flash（约 ¥1~2 / 百万 tokens 输出，按量计费）

## 1. 这个项目解决什么问题

单个 LLM 干长任务有三个结构性毛病：**贵**（思考与执行同一个价）、**不可信**（自己宣布完成，无人验收）、**易失忆**（会话一关状态全无）。

本系统的答案是三个分工：

- **岗位分工**：强模型（K3）只做规划、拆任务、验收；廉价模型（V4-Flash）做全部执行
- **判定分工**："完成"不由工程师宣布，而由**可执行的验收命令**产出的真实证据判定
- **记忆分工**：状态不锁在对话上下文里，全部落盘成**任务卡**（Markdown 文件），可审计、可恢复、可远程驱动

实测账单一角（完整数据见[第 7 节](#7-实验证据与成本数据)）：

| 任务类型 | 架构师成本 | 工程师成本 | 合计 |
|---|---|---|---|
| 5100 字可行性报告（21 条引用） | ¥0.52（走订阅额度） | ¥0.27 | **≈ ¥0.8** |
| 三卡并行演示项目 | ¥0.029 | ¥0.041 | **¥0.070** |
| 静态仪表盘页面（13KB HTML） | ¥0.102 | ¥0.265 | **¥0.367** |

## 2. 核心设计决策（为什么这样设计）

每条决策都有实验记录背书，括号内为证据编号（`compare/实验记录-XXX.md`）。

### 2.1 为什么是两个模型而不是一个？

1. **token 经济学**：一次 agent 任务中"执行"消耗的 token 远多于"规划"（实测 8:1 到 14:1）。
   把大头放在便宜模型上，成本降一个数量级（001、010）。
2. **错误代价不对称**：架构师判断错的代价（方案返工）远大于工程师写错的代价（局部修改）。
   贵的、推理强的模型放判断岗位（002）。
3. **解耦**：两个角色走独立 API，任何一端可换模型/供应商而不动另一端。模型名、端点、
   单价全部在 `config.yaml`，换模型不改代码。

### 2.2 为什么"验收"必须由证据驱动？

LLM 的自汇报不可信。本系统铁律：**绝不让 LLM 替自己做结论**。验收命令真实执行
（`!` 前缀的 shell 命令），架构师读的是执行证据而非工程师自述。

实证：验收曾抓到工程师把 GB 17761-2024 实施日期张冠李戴（2025-09-01 误写为 12-01）——
这种错误读稿子读不出来，只有独立核实能抓到（Harness 线可行性报告任务）。

### 2.3 为什么任务状态要落成"卡片"？

卡片 = Markdown + YAML frontmatter 的任务档案，回答"这单活是什么、干到哪了、凭什么算干完"。
四个作用（006）：

1. **记忆**：状态可恢复可审计，不随会话销毁
2. **交接**：架构师与工程师不共享上下文（防污染 + K3 不可接异源历史），约束必须白纸黑字传递——
   没这层时同一任务曾返工 3 次，有了约束传递后一次通过（003）
3. **价格分界线**：人写卡 = 免费的规划调用。实测手写卡比架构师拆卡省 28~40%（008 vs 007）
4. **并行与远程协作的载体**：GitHub 网页写卡 → 本地 `git pull` → `--cards` 跑完整个项目

### 2.4 并行冲突、死锁、上下文接力怎么解？（经典三问）

| 问题 | 本系统的答案 | 证据 |
|---|---|---|
| 死锁（工程师永远不达标） | 三道防线：单卡返工熔断（上限 2 次）→ 升级人工（escalated）→ 依赖链冻结（下游卡不跑必败任务） | 003、007 |
| 上下文接力（下游任务要用上游产物） | **引用制**：卡片只给文件路径（artifact_refs），工程师按需 read_file——省 token、保注意力 | 007 |
| 并行写冲突（两卡写同一文件） | **不上锁，规划期消灭**：并行卡各写各的文件；共享文件的写入收敛到"集成卡"串行组装（feature branch + merge 的翻版） | 009 |

### 2.5 派几个"员工"由谁决定？

架构师自主决定，由提示词纪律引导（不写死数量，010）：

- **粒度判据**：单卡聚焦单一可独立验收的模块；写不出可执行验收命令 = 拆得不对
- **权衡区间**：太少→单卡超复杂返工烧钱；太多→管理与集成成本爆炸；一般 2~5 个并行为宜
- **强制集成卡协议**：N>1 且成果汇入同一入口文件时，必须生成第 N+1 张集成卡，
  且集成卡只组装、禁止写业务逻辑

实测：面对"四区域仪表盘"任务，架构师按**内聚性**拆成 2 执行卡 + 1 集成卡——
优于机械按区域数拆 4 张（010）。

## 3. 系统架构

### 3.1 四层框架

```
┌────────────────────────────────────────────────┐
│ L4 PM 层：卡盒批量调度（--cards 目录）            │
│    人写卡 / 架构师拆卡 → 依赖排序 → 批量并行       │
├────────────────────────────────────────────────┤
│ L3 并行层：依赖感知调度器                         │
│    depends_on 就绪即派发 · 失败冻结 · 线程池      │
├────────────────────────────────────────────────┤
│ L2 状态层：任务卡 + 成本账本                      │
│    tasks/*.md 生命周期 · cost.jsonl 精确记账      │
├────────────────────────────────────────────────┤
│ L1 执行层：双模型内核                             │
│    K3 规划/验收 · V4-Flash ReAct 执行 · 验证器    │
└────────────────────────────────────────────────┘
```

### 3.2 单卡执行循环（L1 细节）

```
任务卡（todo）
   │
   ▼ 状态置 doing
┌──────────────────┐   工具：read/write/list_dir/run_command
│ 工程师 ReAct 循环  │   （工作目录沙箱 + 命令黑名单 + 轮数预算）
└──────────────────┘
   │ finish（四块结构化回报：改动文件/运行命令/输出摘要/已知风险）
   ▼
验证器：真实执行 `!` 开头的验收命令 → 产出证据（不是模型自述）
   ▼
架构师读证据验收：
  ✓ 通过 → 卡片 done，记录验收理由
  ✗ 返工 → 修复指令写回卡片 + 移交包，预算减半，再来一轮
  ✗✗✗ 连续失败超限 → 卡片 escalated，交还人工；依赖它的卡冻结
```

## 4. 快速开始

### 4.1 环境准备

```powershell
# 1. Python 3.12+，装依赖
pip install openai pyyaml

# 2. 两个 API key 永久存为系统变量（设完重开终端生效）
setx KIMI_API_KEY "sk-kimi-你的订阅key"
setx DEEPSEEK_API_KEY "sk-你的deepseek-key"
```

> 注意：Kimi 订阅 key 只能走 `https://api.kimi.com/coding/v1` 端点、模型 ID `k3`
> （已写在 `config.yaml`，无需手改）。

### 4.2 三种启动模式（MVP 编排器）

```powershell
cd architect-engineer

# 模式一：一句话任务 —— 架构师自动拆卡后并行执行
python orchestrator.py "写一个脚本统计本目录 md 文件行数"

# 模式二：单张手写卡 —— 跳过规划直接执行（省约 40% 架构师成本）
python orchestrator.py --card path\to\card.md

# 模式三：卡盒批量 —— 一整个项目，依赖感知并行调度
python orchestrator.py --cards path\to\cardbox
```

每次运行生成 `runs/<时间戳>/`，内含：`tasks/*.md`（任务卡全生命周期）、
`workspace/`（产物）、`cost.jsonl`（逐次调用账本）、`report.json`（总结）、
`handoffs/`（移交与验收记录）。

### 4.3 Web 版（日常主力）

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File run-dsh-web.ps1
# 自动打开 http://127.0.0.1:3080 ，新开会话即可用大白话派任务
```

事后算账：`python compare\analyze_session.py`（最近一次）或加会话目录路径（指定某次）。

## 5. 任务卡：系统的核心抽象

### 5.1 格式（schema v0.1）

```markdown
---
id: "t1"
title: "一句话标题"
status: "todo"          # todo / doing / done / rework / escalated
owner: "human"          # human / architect / engineer
created: "2026-08-17T15:00:00"
updated: "2026-08-17T15:00:00"
depends_on: ["t0"]      # 前置卡 id，全部 done 才可调度；无依赖写 []
---

## 目标
要做什么（一段话说清）

## 验收标准
- !python test.py        ← 以 ! 开头 = 可执行验收命令，验证器真实运行
- 其余为文字判据，由架构师评判

## 已确认事实与约束
- 工程师看不到你的对话，约束必须写全（如"环境是 Windows，禁用 Unix 命令"）

## 产物引用
- 相关文件路径（引用制：工程师按需自行读取）

## 结构化回报
（工程师完成后由编排器填入：改动文件 / 运行命令 / 输出摘要 / 已知风险）

## 返工与备注
（返工指令、验收理由、升级原因自动追加在这里）
```

### 5.2 写卡纪律（血泪换来的）

1. **并行卡各写各的文件**，禁止并行写同一文件；需要合并就开"集成卡"（009）
2. 验收命令必须是 **Windows 兼容**（python / dir / findstr / python -c），禁用 Unix 命令（003）
3. 约束写全：编码要求、文件格式、"不许做什么"都要写——工程师看不到对话上下文

示例卡盒：`compare/cardbox-demo/`（基础三卡）、`compare/cardbox-conflict/`（集成卡模式）。

## 6. 两条技术路线

| | 路线 A：自建 MVP 编排器 | 路线 B：DeepSeek Harness 移植版 |
|---|---|---|
| 位置 | `architect-engineer/orchestrator.py`（约 550 行） | `harness-patches/` + `dsh-home/.agent-presets/` |
| 底盘 | 自写编排循环 | DeepSeek 官方开源 harness |
| 优势 | 每行可读、逻辑任意改、按 API 返回精确记账、任务卡/并行/卡盒全套 | Web 界面、成熟工具链、会话持久化可回放 |
| 定位 | **实验室**：新想法在这里验证（006~010 全部诞生于此） | **日常主力**：实际干活用它 |
| 启动 | 见 [4.2](#42-三种启动模式mvp-编排器) | `run-dsh-web.ps1` |

两条线共享同一套思想（双模型路由 + 证据验收），实验在两线间互证（001）。

### 6.1 dsh 版本管理（Web 版）

dsh 版本号钉死在脚本的 `$DSH_VERSION`（当前 `0.1.0-rc.6`），不用 `npx -y` 拉最新版——
patch 依赖 harness 内部插件 ID，rc 阶段静默升级会无征兆地坏（403 事件为证）。
升级步骤与信任栅栏排查见 `决策框架.md` 与实验记录。

## 8. 已知边界

- **简单任务不划算**：规划与验收本身消耗 token，一句话能完成的任务走编排反而更贵
- **共享 workspace 无写锁**：冲突靠卡片纪律规避（7.1 节/README 5.2），极端高频冲突再上乐观锁
- **多模态**：K3 图片输入已在 Harness 声明并单独验证可读图，完整含图任务尚未复验
- **工程师无联网工具**（MVP 线）：需要检索的任务走 Harness 线
- **待补实验**：全 K3 单模型基线、多任务统计显著性、失败任务鲁棒性（见 `决策框架.md`）
