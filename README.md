# 双模型 Multi-Agent 工作流：Kimi K3 架构师 + DeepSeek V4-Flash 工程师

> 一套"贵模型思考、便宜模型执行"的双模型 agent 系统。
> 两个角色走两个独立的 API，通过编排机制协作完成任务，全程可审计、可计量。
>
> 本文档面向两类读者：想**使用**这套流程的人，和想**理解它为什么这样设计**的人。

---

## 1. 一句话说明白

用户给一个任务（比如"写一份可行性分析报告"），**Kimi K3 当架构师**：解读需求、拆解任务、制定方案、最后亲自验收；**DeepSeek V4-Flash 当工程师**：写代码、写文档、跑命令、联网检索。两个模型是两个独立的 API 账号，通过"编排"串成一条流水线。

实测一次真实任务的成本账（2026-08-14，5100 字可行性报告）：

| 角色 | 模型 | LLM 调用 | 输出 tokens | 成本 |
|---|---|---|---|---|
| 架构师 | Kimi K3（订阅端点） | 9 次 | 5,125 | ¥0.52（估算，实际走订阅额度） |
| 工程师 | DeepSeek V4-Flash | 25 次 | 39,185 | **¥0.27（真实账单）** |

## 2. 为什么这样设计（设计的"所以然"）

### 2.1 为什么是两个模型而不是一个？

三个原因，按重要性排序：

1. **token 经济学**：一次 agent 任务里，"执行"环节（写代码、跑命令、读文件、改 bug）消耗的 token 远多于"思考"环节（实测约 8:1）。把大头放在便宜模型上，成本降一个数量级。
2. **错误代价不对称**：架构师判断错的代价（方案返工）远大于工程师写错的代价（局部修改）。所以贵的、推理强的模型放在判断岗位上。
3. **可独立替换**：两个角色走独立 API，任何一端都可以换模型/换供应商而不动另一端。这是工程上的"解耦"。

### 2.2 为什么必须有"验收"环节？

LLM 的自汇报不可信——它说"完成了"可能是幻觉、可能半途而废、可能夸大部分成功。本系统的铁律是 **书 2.6 节：绝不让 LLM 替自己做结论**。架构师验收时必须真实执行验收动作（运行脚本、核对数据、独立检索），而不是读一遍工程师的汇报就放行。

实证：验收环节曾抓到工程师把 GB 17761-2024 新国标实施日期张冠李戴（2025-09-01 误写为 12-01），这种错误读稿子读不出来，只有独立核实才能抓到。

### 2.3 为什么派工边界要明示？

架构师的人格指令明确划分："理解需求、拆解任务、制定方案、验收结果"归架构师；"写代码、写文档初稿、跑批量处理"派给工程师。不写清楚的后果实测出现过：面对"读懂一份 PPT"这种任务，K3 判断读文档是"思考"而非"执行"，就自己干完了，工程师全程没接到活。

## 4. 两条技术路线（以及为什么都保留）

| | 路线 A：自建 MVP 编排器 | 路线 B：DeepSeek Harness 移植版 |
|---|---|---|
| 位置 | `architect-engineer/orchestrator.py`（约 370 行 Python） | `harness-patches/kimi-provider.yml` + `dsh-home/.agent-presets/architect-engineer/` |
| 底盘 | 自己写的编排循环 | DeepSeek 官方开源 harness（2026-08-13 发布） |
| 优势 | 每行可读、编排逻辑可任意改（加角色/改验收）、成本按 API 返回精确记账 | Web 界面、成熟工具链（fs/shell/搜索/子代理）、会话持久化可回放 |
| 定位 | **实验室 + 教学标本**：新想法在这里验证 | **日常主力**：实际干活用它 |
| 启动 | `python orchestrator.py "任务"` | `run-dsh-web.ps1` → 浏览器 127.0.0.1:3080 |

选型过程本身是项目的一部分：先用 MVP 跑通证明机制可行，再把同样的双模型路由思想移植到官方 harness，两边用同一任务做对比实验（见 `compare/实验记录-001.md`）。

## 5. 组件清单（这套系统由什么组成）

## 6. 如何使用（速查）

**日常用（Web 版）**：运行项目根目录下的 `run-dsh-web.ps1`（PowerShell），服务起来后会自动打开浏览器 `http://127.0.0.1:3080`，新开会话（预设自动为"架构师+工程师"），大白话派任务。

**事后算账**：
```
python compare\analyze_session.py        :: 最近一次运行
python compare\analyze_session.py <会话目录>  :: 指定某次
```

**前提**：两个 API key 已用 `setx` 永久存为系统变量 `KIMI_API_KEY` / `DEEPSEEK_API_KEY`（Kimi key 是 Kimi Code 订阅 key，只能走 `api.kimi.com/coding/v1` 端点，模型 ID 是 `k3`）。

### 6.1 dsh 版本管理与升级流程

所有启动脚本里 dsh 版本号**钉死在 `$DSH_VERSION`**（当前 `0.1.0-rc.6`），不用 `npx -y` 拉最新版。原因：本项目 patch 依赖 Harness 内部插件 ID 和配置结构（`llm-pi-ai` / `agent-default-model` / `tool-subagent`），rc 阶段这些接口不稳定，静默升级会无征兆地坏（2026-08-17 的 403 事件即为例证：信任栅栏行为在 rc.5→rc.6 间变更）。

**升级步骤**：
1. 看官方 releases（github.com/deepseek-ai/deepseek-harness），确认新版本有你需要的功能/修复，没有就不升
2. 改脚本里的 `$DSH_VERSION`（三个脚本一起改：`run-dsh-web.ps1` / `run-dsh-kimi.ps1` / `run-dsh-test2.ps1`）
3. 验证三连：设置页能打开（无 403）→ 发一条测试任务 → 确认 K3 架构师 + DeepSeek 工程师都在账本里出现
4. 验证通过 → 提交 git；不通过 → 改回旧版本号立即恢复，把问题记进 `compare/实验记录`

**已知坑**：Web 版有浏览器信任栅栏，特权 API（settings.* 等）仅 loopback 可访问；若浏览器/扩展剥离了 Origin 头的端口号会被误判跨站返回 403——用 InPrivate 窗口或换浏览器排查（详见 compare 实验记录）。

## 7. 已知边界与待办

- **多模态**：K3 图片输入已在 Harness 声明（`input: [text, image]`）并单独验证端点可读图，但完整含图任务尚未复验
- **待补实验**（详见决策框架.md 第 4 节）：全 K3 单模型基线（E1）、多任务统计（E2）、失败任务鲁棒性（E4）
- **派工边界**：人格指令对"读文档算思考还是算执行"的界定仍可细化
- **简单任务不划算**：规划和验收本身消耗 token，一句话能完成的任务走编排反而更贵——这套系统有适用边界，不是银弹
