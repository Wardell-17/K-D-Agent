## 1. 这个项目解决什么问题

单个 LLM 干长任务有三个结构性毛病：**贵**（思考与执行同一个价）、**不可信**（自己宣布完成，无人验收）、**易失忆**（会话一关状态全无）。

本系统的答案是三个分工：

- **岗位分工**：强模型（K3）只做规划、拆任务、验收；廉价模型（V4-Flash）做全部执行
- **判定分工**："完成"不由工程师宣布，而由**可执行的验收命令**产出的真实证据判定
- **记忆分工**：状态不锁在对话上下文里，全部落盘成**任务卡**（Markdown 文件），可审计、可恢复、可远程驱动

实测账单一角（完整数据见[第 7 节](#7-实验证据与成本数据)）：

| 任务类型 | 架构师成本 | 工程师成本 | 合计 |
|---|---|---|---|
| 5100 字可行性报告（21 条引用） | ¥0.52（走订阅额度） | ¥0.27 | **≈ ¥0.8** |
| 三卡并行演示项目 | ¥0.029 | ¥0.041 | **¥0.070** |
| 静态仪表盘页面（13KB HTML） | ¥0.102 | ¥0.265 | **¥0.367** |

标准考场实测（GAIA，最权威通用 Agent 基准；全部闭卷、零答案倾向写卡、
考后对照官方答案判卷）：

| 场次 | 题集 | 成绩 | 成本 |
|---|---|---|---|
| mini-bench（030） | Level 1 混编 10 题（检索×4/推理×2/附件×4） | **8/10**（且该场检索工具离线，见 031 勘误） | ¥1.09（单题均 **¥0.11**） |
| 检索专项（031/032） | 同构检索题 6 题 | 断网 2/6 → 有网 **6/6**；双臂复测 5/6 | ¥0.36/场 |
| Meta-Agent 全链路（029） | Level 1 真题单题（总控拷问→审卡→执行→独立复算终审） | **精确命中标准答案** | 编排器侧 ¥0.27 |
| **Level 2 全量（051/052）** | L2 文本+轻附件子集 76/86 题 | **57/76（75.0%）严格判分**，错题 18 道全分类入档 | 全程 **¥15.9**（单题均 **¥0.21**） |

成绩引用口径：以上均为 **GAIA Level 1 文本/表格/代码类子集**（视频/音频题因无对应
工具链被剔除，视觉题实测 0/2 并已完成失败解剖——能力边界如实记录，见实验记录 034）。


## 2. 核心设计决策（为什么这样设计）

每条决策都有实验记录背书，括号内为证据编号（`compare/实验记录-XXX.md`）。

### 2.1 为什么是两个模型而不是一个？

1. **token 经济学**：一次 agent 任务中"执行"消耗的 token 远多于"规划"（实测 8:1 到 14:1）。
   把大头放在便宜模型上，成本降一个数量级（001、010）。
2. **错误代价不对称**：架构师判断错的代价（方案返工）远大于工程师写错的代价（局部修改）。
   贵的、推理强的模型放判断岗位（002）。
3. **解耦**：两个角色走独立 API，任何一端可换模型/供应商而不动另一端。模型名、端点、
   单价全部在 `config.yaml`，换模型不改代码。

### 2.2 为什么"验收"必须由证据驱动？

LLM 的自汇报不可信。本系统铁律：**绝不让 LLM 替自己做结论**。验收命令真实执行
（`!` 前缀的 shell 命令），架构师读的是执行证据而非工程师自述。

实证：验收曾抓到工程师把 GB 17761-2024 实施日期张冠李戴（2025-09-01 误写为 12-01）——
这种错误读稿子读不出来，只有独立核实能抓到（Harness 线可行性报告任务）。

### 2.3 为什么任务状态要落成"卡片"？

卡片 = Markdown + YAML frontmatter 的任务档案，回答"这单活是什么、干到哪了、凭什么算干完"。
四个作用（006）：

1. **记忆**：状态可恢复可审计，不随会话销毁
2. **交接**：架构师与工程师不共享上下文（防污染 + K3 不可接异源历史），约束必须白纸黑字传递——
   没这层时同一任务曾返工 3 次，有了约束传递后一次通过（003）
3. **价格分界线**：人写卡 = 免费的规划调用。实测手写卡比架构师拆卡省 28~40%（008 vs 007）
4. **并行与远程协作的载体**：GitHub 网页写卡 → 本地 `git pull` → `--cards` 跑完整个项目

### 2.4 并行冲突、死锁、上下文接力怎么解？（经典三问）

| 问题 | 本系统的答案 | 证据 |
|---|---|---|
| 死锁（工程师永远不达标） | 三道防线：单卡返工熔断（上限 2 次）→ 升级人工（escalated）→ 依赖链冻结（下游卡不跑必败任务） | 003、007 |
| 上下文接力（下游任务要用上游产物） | **引用制**：卡片只给文件路径（artifact_refs），工程师按需 read_file——省 token、保注意力 | 007 |
| 并行写冲突（两卡写同一文件） | **不上锁，规划期消灭**：并行卡各写各的文件；共享文件的写入收敛到"集成卡"串行组装（feature branch + merge 的翻版） | 009 |

### 2.5 派几个"员工"由谁决定？

架构师自主决定，由提示词纪律引导（不写死数量，010）：

- **粒度判据**：单卡聚焦单一可独立验收的模块；写不出可执行验收命令 = 拆得不对
- **权衡区间**：太少→单卡超复杂返工烧钱；太多→管理与集成成本爆炸；一般 2~5 个并行为宜
- **强制集成卡协议**：N>1 且成果汇入同一入口文件时，必须生成第 N+1 张集成卡，
  且集成卡只组装、禁止写业务逻辑

实测：面对"四区域仪表盘"任务，架构师按**内聚性**拆成 2 执行卡 + 1 集成卡——
优于机械按区域数拆 4 张（010）。

## 3. 系统架构

### 3.1 四层框架

```
┌────────────────────────────────────────────────┐
│ L4 PM 层：卡盒批量调度（--cards 目录）            │
│    人写卡 / 架构师拆卡 → 依赖排序 → 批量并行       │
├────────────────────────────────────────────────┤
│ L3 并行层：依赖感知调度器                         │
│    depends_on 就绪即派发 · 失败冻结 · 线程池      │
├────────────────────────────────────────────────┤
│ L2 状态层：任务卡 + 成本账本                      │
│    tasks/*.md 生命周期 · cost.jsonl 精确记账      │
├────────────────────────────────────────────────┤
│ L1 执行层：双模型内核                             │
│    K3 规划/验收 · V4-Flash ReAct 执行 · 验证器    │
└────────────────────────────────────────────────┘
```

### 3.2 单卡执行循环（L1 细节）

```
任务卡（todo）
   │
   ▼ 状态置 doing
┌──────────────────┐   工具：read/write/list_dir/run_command
│ 工程师 ReAct 循环  │   （工作目录沙箱 + 命令黑名单 + 轮数预算）
└──────────────────┘
   │ finish（四块结构化回报：改动文件/运行命令/输出摘要/已知风险）
   ▼
验证器：真实执行 `!` 开头的验收命令 → 产出证据（不是模型自述）
   ▼
架构师读证据验收：
  ✓ 通过 → 卡片 done，记录验收理由
  ✗ 返工 → 修复指令写回卡片 + 移交包，预算减半，再来一轮
  ✗✗✗ 连续失败超限 → 卡片 escalated，交还人工；依赖它的卡冻结
```

### 3.3 检索层：web_search（可插拔 driver，按任务卡路由）

外部事实类任务（最新政策、甲方官网信息、库的 API 变动）是无检索 LLM 的幻觉重灾区——
模型不会说"我不知道"，只会生成"看起来合理"的内容。本系统的解法是**把检索做成工程师的
标准工具**，而非新增一个"研究员"角色或供应商。

**工作机理**（实验 014 起升级为可插拔 driver 层）：

```
工程师收到涉外部事实的卡（frontmatter 可声明 search_backend）
   │ web_search(query) → 按后端路由
   ▼
┌─────────────────────────────────────────────────────────────┐
│ auto（默认）: Tavily（1000 次/月免费档）→ 失败降级              │
│               DeepSeek 直连官方端点（≈¥0.04/次，usage 自记账）   │
│ tavily      : 只用 Tavily，成本可审计                           │
│ deepseek    : DeepSeek 服务端联网（直连 + 自记账，中文时效最强）  │
│ brave / ddg : 保留注册未入链（Brave 资费否决；ddg 反爬实证不可用）│
└─────────────────────────────────────────────────────────────┘
   ▼
检索结果落盘 research/*.md（引用制：下游卡 artifact_refs 复用，同一资料全项目只查一次）
   ▼
事实写入产物时逐条附 来源 URL + 数据发布时间 → 架构师验收可独立抽查信源真实性
```

**为什么做成可插拔而不是绑死一个工具？**（实验 013 的教训）
工具会过时、配额会耗尽、时效性各有长短——**检索后端是可替换的零件，任务卡与证据链才是核心资产**。
路由优先级：任务卡 `search_backend` 字段 > `config.yaml` 全局默认 > auto 降级链。
指定后端失败时**不擅自跨后端**（保持路由可预期、账本可归因），只提示改卡或换查询词。

**时效性纪律**（013 实测：不带时间约束的查询会抓到 2024 年旧口径）：
工程师系统提示强制要求查询词带时间约束（如「2026年最新」），
结论必须附数据发布时间（精确到年月）——时效性问题在 Prompt 层治理，与后端无关。

**内置的三重省额度机制**（Tavily 免费档 1000 次/月，实测单任务仅耗 5 次）：
查询去重拦截、卡片限定检索范围、引用制缓存复用。额度耗尽自动降级 DeepSeek 直连
（自记账，052 实战验证：Tavily 耗尽后 65 次检索零断供），
"额度焦虑"被转化为架构设计而非信用卡问题。

**为什么选 Tavily 而不是 Kimi 自带检索 / Gemini grounding？**

| 候选 | 排除原因 |
|---|---|
| Kimi 自带 web_search | ① 订阅 coding 端点实测不支持检索协议闭环（048：模型会发起搜索但第二轮一律 400，6 种协议变体全灭）；platform 付费端点官方支持（token + 按次调用费），留作升级位；② 岗位错位——检索是高频执行（单任务约 5 次），挂架构师身上等于用最贵模型吞吐网页原料；③ 证据混在模型对话里，无法独立审计 |
| Gemini grounding | ① 免费档 grounding 配额耗尽即 429（实测）；② 返回经模型摘要的二手结论，不符合"一手证据优先" |
| **Tavily** ✅ | 一手结构化原料（标题+URL+摘要）直接落盘、调用可数可记账、中文官方信源（gov.cn/新华社/人民网）实测可达 |

**实测效果**（实验记录 012，同一张卡 A/B 对比）：
事实正确率 **1/3（禁检索）→ 3/3（带检索）**，B 组每条事实附可核查 URL、零返工，
总成本与 A 组持平（±5%）——**准确性提升约等于免费**。

注：架构师在验收环节偶尔独立检索抽查（低频、高判断含量）是合理的分工补充，
与本工具不冲突——分层依据是频率和判断含量。

## 4. 快速开始

### 4.1 环境准备

```powershell
# 1. Python 3.12+，装依赖
pip install openai pyyaml

# 2. API key 永久存为系统变量（设完重开终端生效；前两个必填，第三个可选）
setx KIMI_API_KEY "sk-kimi-你的订阅key"
setx DEEPSEEK_API_KEY "sk-你的deepseek-key"
setx TAVILY_API_KEY "tvly-你的检索key（可选：不配或额度耗尽时检索自动降级 DeepSeek 直连，自记账 ≈¥0.04/次）"
```

> 注意：Kimi 订阅 key 只能走 `https://api.kimi.com/coding/v1` 端点、模型 ID `k3`
> （已写在 `config.yaml`，无需手改）。

### 4.2 启动方式（MVP 编排器）

先记住一句话：**区别只在"卡片从哪来"**——系统永远是"拿到卡片 → 并行执行 → 证据验收"。
四种方式对应"卡片的四种来源"，按需求清晰度选：

| 方式 | 卡片谁写 | 什么时候用 | 命令 |
|---|---|---|---|
| ① 审批门 | 架构师拆，**人审完才执行** | 需求宏观/模糊（默认推荐，审卡约 1 分钱） | 见下方两步 |
| ② 一句话 | 架构师拆，拆完直接执行 | 需求明确、信得过架构师 | `python orchestrator.py "任务描述"` |
| ③ 单张手写卡 | 人写（零规划成本） | 任务小而具体，自己能写清验收命令 | `python orchestrator.py --card 卡片.md` |
| ④ 卡盒批量 | 人写一目录的卡 | 多卡项目、GitHub 远程写卡本地跑 | `python orchestrator.py --cards 卡盒目录` |

```powershell
cd architect-engineer

# 方式① 审批门（分两步）：第一步只拆卡不执行，卡片落在 runs\<时间戳>\tasks\
python orchestrator.py --plan-only "你的宏观项目描述"
# 人打开 tasks\ 目录审卡/直接改 .md，确认无误后放行：
python orchestrator.py --cards "runs\<时间戳>\tasks"

# 方式②③④ 见上表命令
# 中断恢复：任何方式跑挂了，用 --resume 接 run 目录续跑（done 卡零成本跳过）
python orchestrator.py --resume "runs\<时间戳>"
```

每次运行生成 `runs/<时间戳>/`，内含：`tasks/*.md`（任务卡全生命周期）、
`workspace/`（产物）、`cost.jsonl`（逐次调用账本）、`report.json`（总结）、
`handoffs/`（移交与验收记录）。

## 5. 任务卡：系统的核心抽象

### 5.1 格式（schema v0.1）

```markdown
---
id: "t1"
title: "一句话标题"
status: "todo"          # todo / doing / done / rework / escalated
owner: "human"          # human / architect / engineer
created: "2026-08-17T15:00:00"
updated: "2026-08-17T15:00:00"
depends_on: ["t0"]      # 前置卡 id，全部 done 才可调度；无依赖写 []
---

## 目标
要做什么（一段话说清）

## 验收标准
- !python test.py        ← 以 ! 开头 = 可执行验收命令，验证器真实运行
- 其余为文字判据，由架构师评判

## 已确认事实与约束
- 工程师看不到你的对话，约束必须写全（如"环境是 Windows，禁用 Unix 命令"）

## 产物引用
- 相关文件路径（引用制：工程师按需自行读取）

## 结构化回报
（工程师完成后由编排器填入：改动文件 / 运行命令 / 输出摘要 / 已知风险）

## 返工与备注
（返工指令、验收理由、升级原因自动追加在这里）
```

### 5.2 写卡纪律（血泪换来的）

1. **并行卡各写各的文件**，禁止并行写同一文件；需要合并就开"集成卡"（009）
2. 验收命令必须是 **Windows 兼容**（python / dir / python -c），禁用 Unix 命令（003）；
   涉及中文内容匹配一律用 python（findstr 在 GBK 代码页下匹配 UTF-8 中文必失败）
3. 约束写全：编码要求、文件格式、"不许做什么"都要写——工程师看不到对话上下文
4. **验收标准对工程师完全可见**（026 实锤）：工程师会照着验收答题——写得窄就被"应试"，
   验收标准的质量就是这个系统的交付天花板

### 6.1 dsh 版本管理（Web 版）

dsh 现行版本 `0.1.1-rc.2`（项目内 `npm-global/` 本地安装优先，`run-dsh-web.ps1` 的
`$DSH_VERSION` 仅作 npx 兜底）。**不做版本钉死，做"升级过闸"**——patch 依赖 harness
内部插件 ID，rc 阶段静默升级会无征兆地坏（403 事件为证），但钉死版本意味着放弃
官方修 bug 的红利，故改为机器过闸：

**升级协议（每次 DSH 升级后执行）**：
1. `npm install -g --prefix npm-global @deepseek-ai/dsh@<新版>`（旧版目录即回滚点，
   重装旧版本号即可随时回退）；
2. 跑自动过闸脚本 `python compare\smoke_dsh.py`——七盏灯：
   preset 静态契约 ×2 / 派发链路 ×4 / 端到端烟题 ×4（约 12~30 秒、¥0.01 级），
   红灯自带定位指引；
3. 肉眼确认一次 preset 仍在 DSH 界面列表中（唯一无法自动化的断言，10 秒）；
4. 全绿即放行；patch 若失效按 `决策框架.md` 的信任栅栏清单重打。

架构定位：DSH 是**可替换的哑终端**（收大白话 + run_command + preset 位），
核心资产（编排器/卡片/验收/账本/检索链）全部自持——耦合面只有
"preset 文本 + shell 执行 + 文件约定（tasks/ 进、report.json 出）"三个接口。

### 7.1 近期问题与解决思路（013~017 进化线）

这五轮实验解决了同一主题——**让系统能可靠地"读大代码库"**，问题是一个接一个真实暴露的：

1. **检索时效之争（013→014）**：DSH 原生搜索抓到比 Tavily 更新的数据，一度以为 Tavily
   能力不行。控制变量后实锤是**查询词没带时间约束**——时效性在 Prompt 纪律层治理，
   不是靠换更贵的工具。教训：先怀疑纪律，再怀疑工具。
2. **审批门拦下致命缺陷（015）**：架构师拆的卡要求把产物写到工程师沙箱之外
   （必然全军覆没），且丢了原任务的半壁需求。人工审卡 10 分钟改完，省下 ¥1.15
   的全军覆没。**审批门不是流程负担，是系统最便宜的安全件**。
3. **深读三短板（015 暴露 → 016/017 闭环）**：
   - 预算不足（读 5-8 个大文件就耗尽 12 轮）→ 任务卡 `budget` 字段，卡级覆盖全局默认；
   - 预算耗尽误杀（产物已落盘但被判失败升级）→ `written_files` 取证 + 验收时注入
     `process_note`：只凭证据判定，不因流程收尾缺失否决；
   - 半截文件幻觉（20000 字符截断可能切在关键逻辑中间）→ `read_file` 加 `offset`
     翻页 + 返回头导航（"共 X 字符，剩余 Y 可续读"）+ 系统提示纪律。
4. **中断恢复（015 问题③ → 已修）**：进程被杀后卡片卡 doing，新增 `--resume`：
   done 卡跳过不重跑（零 token），中断卡重置续跑。
5. **免费检索兜底失效（014 附带发现）**：DDG 反爬 202、Bing 返回机器人填充页——
   免费 HTML 抓取不可依赖。系统的应对姿态是**诚实失败**（标注未核实），
   不静默降级到垃圾信源。

### 7.2 近期问题与解决思路（019~023 看板与基线进化线）

这一阶段的主题是**把系统从"能跑"变成"可运营、可度量"**，新颖问题集中在两处：

**A. 人机交互层的契约缺陷（看板线）**

1. **Widget 白名单静默丢弃**：新增"人工验收通过"按钮点了没反应——submit 事件的 action
   白名单没同步加 `resolve`，运行时静默丢弃。教训：**前后端契约必须同一次提交里改**，
   静默失败比报错可怕得多。
2. **陈旧输入重放**：发卡后任务文本留在 Widget 持久化 inputState 里，刷新时被重放，
   把昨天的旧任务重新启动了一个编排器（险些重复烧 token）。修复：发卡后立即清空
   持久输入。教训：**持久化状态是双刃剑，"帮你记住"在自动化系统里就是隐患**。
3. **钉住逻辑自相矛盾**：为防"新 run 抢屏"加了视图钉住，结果心跳请求的也是被钉住的
   旧 run——新 run 永远没机会被发现。修复：心跳拉最新快照、钉住只挡渲染不挡探测。

**B. 度量口径的统计学缺陷（基线线）**

4. **"伪 L 级"陷阱**：任务描述笼统时架构师只批 15 轮预算，重型题掉进轻量桶。
   对策：L 级题必须带跨模块约束 + 硬核断言（编译/pytest 全绿），逼出真实复杂度。
5. **启发式分级三次塌陷**：按预算分桶 → 预算×卡数 → 含卡数规则，历史数据怎么切都
   不均匀（架构师的批预算行为随版本漂移）。最终解：**声明式定级**——让架构师拆卡时
   显式输出 tier+reason，启发式只给历史单兜底。
6. **定级口径漂移（盲测实锤）**：几乎同构的两道题（TS 小库加单函数）一次判 S 一次
   判 M。修复：提示词加**定级锚点**（同构任务必须同级 + 语言陌生度上调半级），
   复测同构题稳定判 M——从"发现不一致"到"修复并验证"全程有 run 证据。

**C. 环境层的暗坑**

7. **管道里有两个 Python**：发卡管道 PATH 解析到 Kimi 托管运行时（无 pytest/numpy），
   验收命令全部改全路径 `C:\Python314\python.exe`；JS/C++ 工具链同理
   （Node 落 D 盘、ziglang 当 C++ 编译器、`-w` 屏蔽警告刷屏）。
8. **老测试框架在新 Node 上全灭**：mitt/fast-deep-equal 等候选仓库的 mocha+esm 加载器
   在 Node 22 直接崩溃——选题纪律：**基线不绿的仓库不配当考题**，弃掉四个换 vitest 系。
9. **脏基线是 L 级头号杀手（025）**：实验残骸未清理的仓库会让工程师反复困惑返工；
   纪律升级——每次实验后 `git checkout + git clean` 恢复靶场原始状态，
   "基线要绿"进化为"基线必须是原始干净状态"。

### 7.3 近期问题与解决思路（029~034 会师·考场·多模态进化线）

这一阶段的主题是**把系统带进标准考场（GAIA），并接受真实评测的拷打**。
核心教训一句话：**基准测试最先测出来的不是模型的分数，而是实验者自己的基础设施漏洞**。

**A. 环境完整性是成绩有效性的前提**

1. **断网诈胡（030→031）**：030 跑出 8/10 后回查移交包才发现——整场考试
   `TAVILY_API_KEY` 根本没注入，web_search 全程静默全灭，检索题全靠模型记忆混分。
   教训一：**静默故障比报错可怕，工具可用性必须进审计**（凭证从注册表兜底已修）；
   教训二：同一批题无网 2/6、有网 6/6 且有网臂成本低 3 倍——**检索可用性是一阶变量**，
   归因前先确认工具在线。
2. **控制台编码能杀死编排器（029）**：GBK 代码页打印 "✗" 直接 UnicodeEncodeError
   崩溃。修法是启动时强制 stdout/stderr UTF-8——一行代码，但没有它就是单点故障。

**B. 评测诚信的三道防线**

3. **评审污染（031 实锤 → 032 修复验证）**：K3 架构师在返工指令里凭训练记忆
   写出"标准答案是 X"——它训练时背过 GAIA 题。修复：评审提示词加禁令
   （返工只许指向取证方法，禁止提示答案内容），032 十二卡零泄露验证通过，
   且意外催生健康行为："返工只逼取证链"，工程师被倒逼找到官方 changelog 条目
   后自行改对。**闭卷纪律必须覆盖评审侧，不只是任务卡**。
4. **请求式纪律证伪（032 双臂 A/B）**：双源交叉验证写成"请遵守"，
   合规率 0/6、成绩无差异——**纪律不断言化就不会被执行**（026 规律的再现）。
   决策：与其断言化加成本，不如把取证把关移进评审侧。
5. **并行写冲突的边界（030 学费 ¥0.35）**：009 的"提示词层纪律消灭写冲突"
   挡不住"十个并行任务被要求写同一个 answer.txt"——纪律治理得了恶意，
   治理不了设计缺陷。发卡器强制唯一文件名。

**C. 多模态：能力边界与判定权结构**

6. **视觉自测 ≠ 视觉解题（033 vs 034）**：产物核验（图表规格核对）100% 可靠、
   单次 ¥0.015；竞赛级视觉推理（翻转棋盘读 FEN、长列表细数）0/2 挂科。
   定位写死：read_image 只做自测降返工，不做解题主力。
7. **判官也会眼花（034 最重要发现）**：K3"经读图核验"把错误的 20 项列表判 pass——
   生产者与判定者共享视觉弱点，错误互洽通过。纯文本时代 pytest 是独立物理判官，
   **视觉时代必须给高风险验收配非视觉独立判据**（如"列表长度=N"的可执行断言），
   视觉核验降级为辅助。
8. **判定权不出让的边界守住**：工程师看图只许自测，"通过"永远架构师签署——
   033/034 全程无破窗，这条铁律在多模态扩展中存活。

**D. 无人值守的基建债**

9. **进程树挂死（034 实锤 → 已修）**：孙进程继承管道写端句柄，
   `subprocess.run(timeout=60)` 形同虚设，编排器两次整体冻结。
   修复：CREATE_NEW_PROCESS_GROUP 立户口本 + 超时 taskkill /T 抄家，
   复刻场景 15 秒自醒。**"挂死"降级为"一条工程师可读的错误文本"**。
10. **resume 两次实战救命（029/034）**：断点续跑从"设计好的出口"变成
    "真实救场两次的机制"——但进程树治理修完后，它应该回到备用位置。

### 7.4 近期问题与解决思路（035~046 基线与验收保真进化线）

这十二轮实验解决了同一主题——**让系统的账本可信**：从"跑得出"到"每个对外数字都有证据链"。

1. **六宫格方法论（035→044/046）**：成本基线不按单数堆砌，按「级别 × 拟卡方式」
   分格采样，每格定目标 n（自主 ≥3 / 人工 ≥2），不达标不对外报价。
   底层台账 `compare/基线-六宫格-v0.md`，统计脚本 `compare/tier_stats.py` 可重复跑。
2. **验收证据保真的三次失守（036→041→045，层层递进）**：
   - 036：**命令不存在**——自主拆卡的验收含占位符/猜测路径，验证器根本没东西可跑；
   - 041：**命令失真**——内联 `-c` 断言的嵌套引号在 cmd 链中转义变形，验收在失真命令下"空过"；
   - 045：**命令零执行**——人工卡用 markdown 反引号包裹验收命令，解析器零匹配，
     空证据 vacuous pass（`all([])==True`），系统报告全绿而产物全线 404。
   - 三层治理：验收落地纪律（036）→ 断言一律落盘 .py（041）→ 验证器双保险
     （剥反引号 + 零命令判 False，045）。**每一层都是独立复验逮住的，不是系统自报的**。
3. **规划溢价两组同题对照（035/038、046/043）**：人工拟卡 vs 自主拟卡，
   增量题省 ¥0.79、迁移题省 ¥0.46——溢价与任务"侦察/执行"占比正相关，
   执行层重活人工卡也省不了。自主拟卡的规划税 ≈ ¥0.5~0.8/单，换来零人工设计成本。
4. **L 档分子类定价（040~043）**：L-code（¥1.14~3.14）与 L-read（¥1.78~4.06）
   价差显著，混算均值对两类都会误报；code 类内部再分增量开发（¥1.1~1.3）
   与存量迁移（¥3+，043 实证）。

### 7.6 近期问题与解决思路（047~050 检索层供应商治理进化线）

这四轮实验是"**否定性结论 → 工程绕道 → 实战验证**"方法论的完整样本——
检索层从"能用"走到"每一分钱可审计、每一级降级都有证据"。

1. **Brave 入链又出局（047→048 勘误）**：为解决 Tavily 单点额度焦虑引入 Brave 作二级
   降级池，随后核实其 2026 年初已取消真免费档（新用户仅 $5/月额度）——**成本纪律
   否决供应商**，driver 保留注册但移出 auto 链，不因沉没代码而保留错误架构。
2. **方案 B 端点冒烟（048，否定性结论）**：假设 K3 订阅 coding 端点支持 `$web_search`
   闭环则检索可零成本前移到架构师侧。冒烟实证：端点接受工具声明且模型发起搜索
   （单次约 7500 tokens），但第二轮回传 6 种协议变体全部 `400 tokenization failed`——
   这不是参数问题，是产品分层（检索闭环是 platform 付费端点能力）。**结论如实入档，
   避免了在错误路线上继续投入。**
3. **记账缺口的正确解法（049）**：DSH 自带检索"计费不明"的根因是其框架内 TokenMeter
   不记检索那次 model turn（exp015 逆向实证）——缺口在 DSH，不在 DeepSeek 端点。
   故 `_search_deepseek` 改为**直调官方端点 + 自建 `_ACTIVE_TRACKER` 钩子自记账**，
   检索以独立角色 `engineer-search` 落 cost.jsonl。冒烟绿灯：单次检索 ≈¥0.04，
   中文官方信源一手可达。
4. **端到端实战（050）**：PMI 双月环比检索题一次通过（¥0.0582 / 35 秒），
   auto 链一级 Tavily 生效、二级 DeepSeek 待命；验收用拟卡人预置断言脚本
   （045 教训固化），锚点数值与官方"环比降 1.1 个百分点"交叉一致。

最终形态：`Tavily（免费档）→ DeepSeek 直连（自记账）→ 诚实失败`；
中文重时效题卡级指定 deepseek；Kimi platform key 为已验证的升级位。

5. **降级链的实战验收（052 附赠证据）**：L2 全量跑到第 8 分钟 Tavily 免费档耗尽，
   auto 链无声切换 DeepSeek 直连，65 次检索 ¥2.00、73 题零断供——
   "降级"第一次不是设计图而是生产事实。

## 8. 已知边界（按层次深挖）

- **下界：编排税**。规划+验收有固定成本（约 ¥0.02~0.05），一句话能完成的任务走编排反而更贵。
  值得编排的任务特征：多环节、有客观成败标准、出错代价高。
- **上界：工程师能力天花板**。高难度算法/大型重构会撞墙熔断——系统把"工程师能做的事"变得
  极便宜极可靠，但不能让廉价模型做超出能力的事；升级人工是设计好的出口。
- **最隐蔽的边界：验收可表达性**。验证器只执行客观命令——代码类任务证据链最强；文案/设计类
  只能靠架构师读，弱一档。心法：尽量把验收标准写成可执行命令，或让架构师把主观判断转化为
  可核查事实（如独立检索核实数据）。
- **上下文边界**：工程师读文件单页 20000 字符（成本防线），但已支持 offset 翻页 +
  返回头导航（017 实测工程师会自发"先定位符号再跳页"）；拆卡时仍要保证输入/产物"可咀嚼"。
- **工具边界**：工程师已配 `web_search`（可插拔后端：auto（tavily→deepseek）/tavily/deepseek
  /brave（保留未入链）/ddg（占位），任务卡级路由 + 查询去重，实验 012/014/049）；
  无视觉能力，含图任务走 Harness 线（K3 读图）
- **审核者本身会错**：架构师也是 LLM，文字判据部分依赖其判断力——最终兜底永远是人，
  因此系统提供 `--plan-only` 审批门：执行前人工审卡，把纠偏成本降到零。
- **共享 workspace 无写锁**：冲突靠卡片纪律规避（见 5.2），极端高发再上乐观锁。
- **多模态**：双侧已闭环——判定侧 K3 验收读图（028），执行侧工程师 `read_image` 自测
  （033，卡级 `require_visual` 授权，单次 ≈¥0.015）；铁律不变：视觉自测不享有判定权。
- **定级有一致性误差**：任务复杂度分级（S/M/L）由架构师判断，曾实锤同构题判级漂移（023）；
  已用"定级锚点"提示词约束并复测验证，但样本仍少，分层均值只能作量级参考而非精确报价。
- **待补实验**：全 K3 单模型基线、多任务统计显著性、失败任务鲁棒性（见 `决策框架.md`）。
