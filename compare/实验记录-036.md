拟卡、拆卡、验收设计全部交给系统自主完成，与 035（人工拟卡、结构已验证）形成 A/B 对照。

## 根因：验收命令"未落地"（grounding failure）

架构师在**侦察完成之前**拆卡，把未验证的路径/占位符写进了可执行验收命令：

1. **t3（前端）**：验收命令写死 `...\frontend && npm run build`——仓库真实目录是 `client/`。
   卡片留了兜底文字"若不为 frontend 则替换验收命令中的路径"，但**验证器是字面执行的机器，
   没人执行替换** → 每条验收命令都报"系统找不到指定的路径" → 两轮预算耗尽 → 升级。
2. **t2（后端）**：验收命令 2 直接含字面占位符 `<后端入口按ANALYSIS.md填写>`，
   验证器原样执行报 `[Errno 22] Invalid argument` → 评审按"证据失败必须返工"正确打回，
   但**工程师无权改卡片里的验收命令**，怎么返工都是错 → 死循环 → 升级。
3. t4 因前置失败级联冻结。

次级问题：t1 把仓库复制到了 `D:\agent-project\workspace\`（run 目录之外），
偏离 run 隔离纪律（未造成事故，但污染了共享目录）。

工程师侧次级问题：t3 首轮 15 轮预算大量烧在碎片化 `python -c` 补丁试探上，
没有直接编辑文件——小预算卡 + 陌生前端文件时的低效模式。

## 结论与治理方向

- "验收标准即天花板"（026）升级为：**验收命令必须基于拆卡时已验证的事实（grounded acceptance）**。
  占位符与猜测路径进入 `!` 命令 = 埋雷，且地雷在工程师无权拆除的位置。
- 治理候选（待定）：
  a) 拆卡纪律：`!` 命令禁止含占位符与未验证路径，只能写拆卡时即可确认的事实；
  b) 结构性解法：两阶段规划——侦察卡先跑，架构师读到侦察产物后再定稿下游卡的验收命令；
  c) 轻量替代：验收命令用"入口自发现"写法（如 `cd 仓库 && .venv/Scripts/python.exe -m pytest`），
     不引用具体文件名。
- 本次 A/B 的直接证据：同一系统、同一题目，拟卡质量差异导致成本差 4.3 倍、
  结果从全绿变 3/4 升级——**规划阶段的事实核查是这个系统最大的成本杠杆**。
