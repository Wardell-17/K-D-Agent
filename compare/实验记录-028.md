# 实验记录 028 ｜ 多模态闭环第一条腿：架构师 K3 读图验收

**日期**：2026-08-24 ｜ **动机**：系统的"断言法庭"此前只管得到纯文本世界
（exit code、pytest、文件断言）；一旦产物是图（图表 / UI / 渲染结果），
验收环节是瞎的，只能信工程师的口头描述。DeepSeek 于 2026-08-21 发布
视觉模型（官方事实见下），多模态议题从"要不要做"变成"怎么做"。

## 设计决策：两条腿，判定侧先行

| 腿 | 内容 | 状态 |
|---|---|---|
| 第一条腿（本实验） | 架构师 K3 验收时直接读图核验 | ✅ 实测通过 |
| 第二条腿（待做） | 工程师 `read_image` 工具 + 任务卡 `require_visual` 字段，执行侧视觉自测 | ⏳ 未开工 |

**关键架构裁定**：驳回了 Gemini 提出的"工程师看图后自行宣布通过"方案。
理由：本系统铁律 2.2 是"判定权与执行权分离"——工程师永远是被审方，
它可以自测、可以修，但"通过"二字只能由架构师签字。视觉能力进入
执行侧只用于**降低返工轮次**（自己看出图错了就地重画），
**不转让判定权**。这一原则同步写进了 `architect_review.md` 的验收纪律。

## 官方事实（2026-08-21 发布，已检索核实）

- 模型 id：`deepseek-v4-flash-vision-exp`
- 文本能力与 V4-Flash 持平；视觉 Agent 基准接近 Opus 4.8
- **计费与 V4-Flash 相同，单张图 ≤384 tokens（≈¥0.0004/张）**——
  Gemini 担心的"视觉 tokens 吞掉成本优势"被官方定价直接化解，
  原先设想的 `require_visual` 成本闸门仍然是好设计（防滥用），
  但不再是经济性刚需
- DSH 侧接入需在 settings.yaml 声明 `input: [text, image]`；
  DSH 官方已连发 rc.7 / rc.8 / 0.1.1-rc.1 支持多模态（升级闸待走）

## 改动

1. **`orchestrator.py`**：
   - `ask_json` 的 user 参数支持多模态 content 列表（str 与 list 双分支，
     纯文本任务路径不受影响）
   - 新增 `collect_image_parts(workdir, written)`：从工程师本轮写入的
     产物里收集图片（png/jpg/jpeg/gif/webp，最多 4 张、单张 ≤5MB），
     base64 内联为 OpenAI `image_url` 部件
   - `_execute_packet` 验收环节：产物含图时把 review 输入改为
     [文本 + 图片部件]，并发 `📷 附图 N 张进验收` 事件
2. **`prompts/architect_review.md`**：携带图片附件时直接查看核验；
   图文矛盾以亲眼所见为准；reason 须注明"经读图核验"。

## 实测（run 20260824-111249）

测试卡 `compare/exp028-card.md`：matplotlib 柱状图，规格钉死——
标题"KD-028 视觉验收"、类别 A/B/C 值 3/7/5、纯红色、6×4 英寸 @100dpi。

- 工程师 15 次调用、架构师 1 次调用，一次通过，无返工

  三根柱子类别 A/B/C、柱顶数值标签 3/7/5 与规格一致，柱子为纯红色，

  K3 的读图描述与图像事实完全一致——是真核验，不是套话。

## 结论

判定侧的视觉闭环已打通：从"产物是图就只能信口述"变成"架构师亲眼验货"。
成本层面视觉核验几乎免费（单张图 <¥0.0005）。剩下的第二条腿
（工程师执行侧自测）属于效率优化而非闭环缺口，优先级让位于
DSH 会师主线（027 用户实测收尾 + 升级闸 rc.6→0.1.1-rc.1）。
