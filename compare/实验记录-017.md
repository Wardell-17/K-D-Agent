# 实验记录 017 —— 翻页纪律实测：17.6 万字符单文件库逆向（read_file offset 首航）

- 日期：2026-08-19
- 实验人：Wardell
- 关联：read_file 截断讨论（"半截文件会不会导致幻觉"）→ offset 翻页机制上线 → 本实验检验"纪律写进提示词是否真被遵守"

## 考题

单卡、15 轮预算：深读 bottle.py（单文件 Web 框架，175882 字符 / 4584 行 ≈ 9 页），
逆向四部分架构（核心类 / 路由匹配 / 请求生命周期 / 服务器适配层），
输出 bottle_architecture.md。

**陷阱设计**：验收强制要求描述 `FileUpload`（@103482）、`WSGIRefServer`（@132861）、
`GeventServer`（@139494）——三个全部位于文件 10 万字符之后的符号。
不翻页读到第 6~7 页，物理上不可能通过。

## 结果：一次通过，翻页行为真实发生

| 指标 | 数值 |
|---|---|
| 工程师 LLM 调用 | 14 次（15 轮预算内） |
| 成本 | ¥0.2866 |
| 验收 | 3 道命令 + 架构师审查全过，零返工 |

工程师的策略（从结构化回报还原）：

1. **先用 run_command 做符号定位**：python 扫出 Router@7915、ServerAdapter@131575、
   FileUpload@103482 等十余个符号的字符偏移——把"顺序翻 9 页"变成"按图索骥"，
   这正是卡片约束里教的"把预算花在刀刃上"；
2. **精准跳页阅读**：read_file offset 取了 7400 / 37406 / 98295 / 103200 / 131300 /
   151300 / 171300 等 8 段，覆盖文件前中后全部关键区域，没有平均用力；
3. **产物质量**：深位符号描述经人工对账属实（FileUpload 的 filename 安全归一化与
   save() 与源码一致；LocalRequest 线程本地机制、Router 正则编译、run() 的
   server_names 解析链等细节均准确）。

产物：`compare/exp017-deliverable-bottle_architecture.md`（16KB）。

## 结论

- **"半截文件幻觉"治理闭环验证通过**：offset 参数 + 返回头导航（"共 X 字符，剩余 Y
  可用 offset 续读"）+ 系统提示纪律（"禁止凭半截文件臆测全貌"）三件套，工程师
  不仅会翻页，还自发升级出"先定位符号再跳页"的省 token 策略。
- **20000 字符成本防线与深读能力不再矛盾**：截断从"静默丢信息"变为"显式可导航"，
  防线仍在（单页上限），但信息可达性完整。
- 至此 015 暴露的深读短板全部闭环：budget 卡级字段（016 首航）+ offset 翻页
  （017 首航）+ 预算耗尽不误杀（015 当班修复）。
