# 对比实验 001：自建 MVP 编排器 vs DeepSeek Harness 移植版

日期：2026-08-14 ｜ 任务：见 task.txt（写 scan_files.py 统计扩展名并生成 report.html，要求实际运行验证）

## 结果

| 维度 | MVP 自建编排器 | Harness 移植版 |
|---|---|---|
| 结果 | ✅ 一次通过（验收 3 条命令全过） | ✅ 通过（架构师独立验收 + 数据核对） |
| 架构师模型 | Kimi K3（coding 订阅端点） | Kimi K3（同一 key） |
| 工程师模型 | DeepSeek V4-Flash | DeepSeek V4-Flash |
| 架构师调用 | 2 次 / 2,044 tokens | 5 次（会话日志 finish 事件计数） |
| 工程师调用 | 9 次 / 26,591 tokens | 9 次（同上） |
| 耗时 | ~46 秒（11:25:08 → 11:25:54） | ~81 秒（会话首尾事件差）+ 进程启动 |
| 成本 | ¥0.0304（精确到 token） | 无法精确计量（订阅端点不返回 usage，Harness 会话日志不含 token 数） |
| 产物隔离 | runs/<时间戳>/workspace 自动隔离 | 当前工作目录，需自行建目录 |
| 可审计性 | report.json 含完整提示词/验收命令/成本 | 会话 jsonl.zstd 全事件流，含每次工具调用与 reasoning |

## 结论

1. 两条链路都能完成真实任务并自我验收，成功率打平（样本量 1，待更多任务累积）。
2. MVP 的核心优势是**成本可计量、产物自动隔离、验收逻辑完全自主**——这是简历上"从零设计编排循环"的卖点。
3. Harness 的核心优势是**工具链成熟（fs/shell/子代理/沙箱）、有 Web UI、会话持久化可回放**——日常使用更顺手。
4. 工程师角色两边都稳定落在 DeepSeek V4-Flash，验证了"贵模型思考、便宜模型执行"的路由假设。
