## 裁决结果

### 标准 ① 官方信源准确度

| 事实 | B 组（Tavily） | C 组（DSH 原生） |
|---|---|---|
| GB 17761-2024 实施日期 | ✅ 2025-09-01，新疆工信厅链接 | ✅ 2025-09-01，地方市监局链接 ×2 |
| 全国保有量（工信部口径） | ✅ 3.8 亿，人民网链接 | ✅ 3.8 亿，中新网/光明网链接 |
| 深圳保有量 | ✅ 550 万（**2024-08** 口径），sz.gov.cn | ✅ **600 万+（2026-01 最新口径）**，南都/读特链接 |

**C 组略胜**：两边都 3/3 正确且带可核查 URL，但 DSH 原生抓到了更新的深圳口径
（600 万 vs 550 万）。差距不大，属于同一量级。

### 标准 ② 总成本

| | B 组（MVP+Tavily） | C 组（DSH 原生） |
|---|---|---|
| 检索执行者 | DeepSeek 工程师（按量付费） | **K3 架构师亲自检索**（订阅额度） |
| tokens | 工程师 39,958 + 架构师 1,439 | K3 单边 48,041（输入含大量缓存命中） |
| 检索调用 | Tavily ×5（免费档额度内） | web_search ×3（后端实为 deepseek-v4-flash 服务端，**usage 未计入账单**） |
| 账面成本 | **¥0.0608** | **¥0.2092**（K3 估算值，订阅口径） |

## 结论：Tavily 保留，DSH 线不动——分工不同，不是胜负关系

用户裁决逻辑："DSH 完胜或打平就删 Tavily"。实测结果**既非完胜也非打平**：

- **信源质量**：DSH 原生略优（ freshness 一档）——得 1 分
- **成本结构**：MVP+Tavily 优 3 倍以上，且 DSH 侧检索由贵模型亲自下场，
  违反我们"检索是高频执行、归工程师"的岗位纪律（010/012 反复验证的原则）
- **可审计性**：Tavily 调用次数可数、结果落盘；DSH 检索后端的 LLM 调用"无 usage 记录"，
  账本有黑洞

**最终架构**：Tavily = MVP 线标准检索工具（工程师工具）；DSH 原生搜索 = Harness 线日常主力
（反正免费包含、质量好）。各归各位，互不替代。

## 本次排障的三个真坑（dsh 凭证体系）

1. **凭证服务遮蔽环境变量**：dsh-llm-deepseek 源码逻辑——credentials 服务存在但无记录时
   直接抛 MISSING_CREDENTIAL，**不回落环境变量**（有 service 就只看 service）。
2. **settings.yaml 覆盖 patch**：Web 引导写入的 agent-default-model（deepseek-official）
   优先级高于 patch 的 kimi-code/k3，启动即校验失败。已改回 kimi-code/k3。
3. **修复方式**：写入 `$DSH_HOME/.credentials.yaml`（Key: value 映射，owner-only 权限），
   已加入 .gitignore。同时为子代理声明了 `deepseek-direct` provider（env 直连）作为双保险。

## 附带发现

- dsh 原生搜索后端 = DeepSeek 自家的搜索增强接口（`/anthropic/v1` 端点 + deepseek-v4-flash，
  maxUses 5/次任务）——它本质是"DeepSeek 模型在服务端联网"，这也解释了 freshness 优势。
- DSH 侧工程师子代理两次未实际参与（spawn 失败 + 架构师单干），DSH 的派工纪律仍需打磨。
