# 实验记录 006 —— MVP 编排器改造为"任务卡驱动"

- 日期：2026-08-17
- 实验人：Wardell（Kimi 协助）
- 关联：实验记录 003（MVP 首跑）；任务卡驱动概念来自外部多 Agent 协作模式讨论

## 目的

把 MVP 编排器（orchestrator.py）从"对话内 JSON 移交包"升级为"任务卡驱动"：
子任务以 Markdown + YAML frontmatter 的卡片落盘，状态（todo/doing/done/rework/escalated）
由代码维护流转，工程师的结构化回报写回卡片——让跨角色协作状态持久化、可读、可审计。

## 改造内容（orchestrator.py，约 +90 行）

1. 新增 `TaskCard` 数据类：frontmatter 六字段（id/title/status/owner/created/updated），
   正文六节（目标 / 验收标准 / 已确认事实与约束 / 产物引用 / 结构化回报 / 返工与备注），
   提供 `render()` / `save()` / `touch()`。
2. 架构师拆任务后，每个子任务先落成卡片（status=todo），打印卡片路径。
3. 工程师执行前 status→doing；finish 后编排器把结构化回报（状态/总结/工具调用计数）写入卡片。
4. 验收 pass→done 并记录验收理由；rework→卡片备注追加修复指令；escalated→owner=human。
5. report.json 新增 `cards` 字段列出全部卡片路径。
6. 兼容性：verify / 预算 / 升级逻辑全部未动；卡片是新增产物层。
   工程师仍不能写工作目录外的文件，因此卡片由编排器代写（有意为之的安全边界）。

## 结论

- 卡片驱动改造一次跑通，单次演示任务成本约 3 分钱，与改造前（记录 003 复跑 ¥0.0252）基本持平——
  卡片读写由代码完成，不增加 LLM 调用。
- 工程师在 finish 纪律约束下能稳定输出四块结构化回报，可直接回写卡片，无需额外解析。
- 卡片即"共享状态"：事后任何人打开 tasks/ 目录即可还原每个子任务的完整生命周期，
  为后续"PM 统一编排 + 多 Agent 并行"预留了状态载体。

## 踩坑清单

1. Git Bash 环境变量展开会吃掉 PowerShell 的 `$env:`——跨 shell 调用必须走 .ps1 文件
   （复用 `compare/run-mvp.ps1`），不能在 bash 单行里内联 PowerShell 变量。
2. 工程师 Toolbox 限制在工作目录内，卡片在 runs/<ts>/tasks/ 属于目录外——
   卡片回写由编排器完成而非工程师自己写，既保住安全边界又实现结构化回报落盘。

## 复现方式

```powershell
# 任务写入 compare\task.txt（UTF-8），然后：
powershell -NoProfile -ExecutionPolicy Bypass -File D:\agent-project\compare\run-mvp.ps1
# 查看卡片：
Get-Content D:\agent-project\architect-engineer\runs\<时间戳>\tasks\card-t1.md
```
