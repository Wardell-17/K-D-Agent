# 实验记录 009 —— 并行写冲突的治理（规划期规避 + 集成卡）

- 日期：2026-08-17
- 实验人：Wardell（Kimi 协助；议题来自 Gemini 秘书梳理的三问之第三问）
- 关联：实验记录 007（踩坑清单第 2 条：共享 workspace 无写锁）

## 背景

调度器并行执行多张卡，但共享 workspace 没有文件写锁：两张并行卡写同一文件会互相覆盖，
且可能各自验收通过（静默丢数据）。本次实施治理方案 A+B：

- **A 规划期规避**：架构师拆卡提示词加入"文件隔离纪律"——并行子任务禁止写同一文件；
  需汇入同一文件时必须拆出 depends_on 各产出卡的"集成卡"。
- **B 工程师纪律 + 文档约定**：工程师人格加入"只写卡片授权的文件"；
  README 7.1 节写明手写卡盒的冲突处理指南。
- （C 乐观锁：暂不实施，冲突高发再上。）

## 验证方法（故意构造冲突场景）

卡盒 `compare/cardbox-conflict/` 复刻 Header/Footer 场景：

- `header.md`：写 header.txt，卡上明示"严禁代写 app.txt"
- `footer.md`：写 footer.txt，同样隔离
- `integrate.md`（depends_on: [header, footer]）：唯一被授权写 app.txt 的卡

运行目录：`runs/20260817-161720/`

## 结论

冲突治理不需要重型锁机制：**纪律写在卡里 + 共享文件写入收敛到串行集成卡**，
在提示词层就把冲突消灭了。这比运行时加锁便宜得多（锁会引发返工重试，返工烧的是 token）。
至此 Gemini 三问全部有答案：死锁→熔断+冻结（007 前已内置）、上下文接力→引用制（007 验证）、
写冲突→隔离+集成卡（本篇验证）。

## 踩坑清单

1. 纪律生效的前提是"写进卡片/提示词"，口头约定对 LLM 无效——confirmed_facts 里的
   "严禁代写 app.txt" 是硬约束载体。
2. 集成卡模式的代价是多一张卡（约 ¥0.015），换来的是零覆盖风险，性价比成立。
