# 实验记录 002：Web 模式链路修复与可行性报告任务（失败驱动的迭代案例）

日期：2026-08-14 ｜ 任务：《在社区推广电动自行车集中充电棚的可行性分析报告》（K3 解读命题+搭框架+验收，DeepSeek 写初稿）

## 经过（完整的 假设→失败→定位→修复→复验 循环）

1. **初测失败**：下午用"解构含 12 张图的 PPT"任务在 Web UI 实测，read_image 报"k3 不支持图像输入"，且子代理跑在 K3 上
2. **定位出两个独立问题**：
   - **能力门控**：read_image 检查路由的 inputModalities，而 k3 的 provider 声明（手写进 patch）缺 `input: [text, image]`；直接用 curl 绕开 Harness 发测试图，K3 端点正确回答"红色"→ 证明是 Harness 侧声明缺失，不是端点能力缺失
   - **路由穿透**：Web 模式会话走 preset 体系，preset 内部的 tool-subagent 是独立实例，外层 patch 的 agentOptions 穿不透 → 子代理继承主会话模型
3. **修复**：
   - patch 补 `input: [text, image]`（--dump-config 验证合并）
   - 按 dsh-agent-presets 官方机制，复制 standard 预设到 `DSH_HOME/.agent-presets/architect-engineer/`，在预设内部改人格（架构师）+ 子代理路由（deepseek-v4-flash）+ 工程师人格，并将 agent-presets.default 指向它
4. **复跑**：换边界更清晰的新任务（可行性报告），链路闭环

## 结果（账本，analyze_session.py 实测，已含 token 级成本）

| 角色 | 模型 | LLM 调用 | 工具调用 | 输入 tokens（缓存命中） | 输出 tokens | 估算成本 |
|---|---|---|---|---|---|---|
| 架构师 | kimi-code/k3 | 9 | 12 | 16,739（命中 108,800） | 5,125 | ¥0.5172（订阅估算值，实际按订阅额度计） |
| 工程师 | deepseek-v4-flash | 25 | 59 | 44,361（命中 961,280） | 39,185 | **¥0.2706（真实按 token 计费）** |

**单任务真实总成本约 ¥0.79**（其中只有 DeepSeek 部分是真实账单），产出 5100 字可行性报告 + 21 条核实过的参考资料。

副产品发现：缓存命中率极高（工程师 96% 输入走缓存），长会话多轮工具调用的成本结构里，缓存折扣是省钱主力——这正是"工程师用便宜模型+高缓存"组合的经济性来源。

产物：`D:\agent-project\harness-test2\feasibility.md`（约 5100 字，21 条参考资料）、`outline.md`（九章框架）

## 结论

1. Web 模式双模型链路修复成功，假设"贵模型稀用、便宜模型狠用"得到第二次验证（调用比 9:25）。
2. 遗留观察项：初测时 K3 曾选择不派工（读 PPT 算"思考"不算"执行"）——人格指令对派工边界的界定仍可细化，记入后续优化清单。
3. 多模态：image 输入声明已生效，但本次任务未含图片，读图链路未复验——待下次含图任务验证。

## 附：踩坑清单（面试可讲）

- OpenAI 兼容层的 `developer` 角色 vs K3 端点（400 报错，源码定位在 pi-ai openai-completions.js）
- Harness 会话日志为多 zstd 帧追加格式（需按魔数切帧解码）
- 子代理 finish 事件不带模型信息（需从 request/context 回推路由）
- preset 作用域隔离导致外层 patch 不穿透（读官方 README 找到 .agent-presets 用户根目录机制）
- Windows GBK 代码页导致 PowerShell 中文脚本乱码（任务文本改走 UTF-8 文件传递）
