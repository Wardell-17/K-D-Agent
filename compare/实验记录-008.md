# 实验记录 008 —— PM 卡盒批量模式（台阶 3，系统闭环里程碑）

- 日期：2026-08-17
- 实验人：Wardell（Kimi 协助）
- 关联：实验记录 006（任务卡驱动）、007（并行调度）

## 目的

实现 `--cards <目录>` 模式：把一叠手写任务卡丢进目录，编排器读卡 → 按依赖排序 →
并行调度 → 批量验收 → 状态回写。至此"GitHub 网页写卡 → 本地 pull → 一条命令跑完一整个
项目"的远程协作流完整成立，任务卡驱动 + PM 编排 + 多 Agent 并行 + 仓库文档共享状态
四层框架全部落地。

## 改造内容

1. 新增 `run_cards(cards_dir)`：读目录下全部 .md 卡（校验 id 唯一），登记后统一交给
   `_schedule()` 调度（复用台阶 2 的依赖感知并行逻辑，零重复代码）。
2. CLI 增加 `--cards <目录>` 入口。三种启动方式齐备：
   - `python orchestrator.py "任务"` —— 模糊需求，架构师拆卡后并行跑
   - `--card 卡.md` —— 单张手写卡，跳过规划直接执行（省 40% 架构师成本）
   - `--cards 目录` —— 卡盒批量，完整 PM 模式

## 结论（里程碑）

四层框架全部落地：

- L1 执行层：K3 规划/验收 + V4-Flash 执行 + 验证器闭环（记录 003）
- L2 状态层：任务卡持久化共享状态 + 精确成本账本（记录 006）
- L3 并行层：依赖感知调度 + 失败冻结（记录 007）
- L4 PM 层：卡盒批量模式，人通过仓库中的卡片直接驱动整个系统（本篇）

简历一句话版本：**本地优先、任务卡驱动、依赖感知并行的双模型多 Agent 协作系统——
强模型只做规划与验收，廉价模型承担高频执行，状态全部落盘可审计，单次演示任务成本约 5 分钱。**

## 踩坑清单

1. 卡 id 必须目录内唯一，载入时强校验（重复即报错，不静默覆盖）。
2. 卡盒里的卡 owner 通常为 human（人写的），执行时正常流转即可，无需特判。
