## 双重根因（均已实锤）

### 根因①：验证器真空漏洞（orchestrator 层，已修复）

人工卡片把验收命令写成 markdown 内联代码格式（`` `!cd ...` `` 带反引号），
`verify()` 只认裸 `!` 前缀 → 零条命令被解析执行 → `ok` 初值 `True` 从未被推翻
→ **空证据 vacuous pass**（`all([])` == True 的经典逻辑陷阱）。
架构师看到 all_passed=true 放行，验收法庭形同虚设。

**修复（orchestrator.py）**：解析时剥反引号；零条可执行命令时判 False 并附
"验收无法成立"证据条目。三场景冒烟验证通过（反引号可解析/无命令判 False/真失败判 False）。

### 根因②：人工拟卡引入错误事实（流程层）

拟卡人把"注册/登录/刷新"错标在 `api/auth.py`，实际注册在 `api/user.py`
（`POST /api/users`，router prefix `/users` + `@router.post("")`）。
工程师严格执行卡内事实写了 `/api/auth/register` → 全线 404。

**纪律教训**：人工拟卡不是免检产品——卡片中的"已确认事实"必须逐行对源码核实，
错误事实 + 忠实执行 = 错得比自主拟卡更彻底。

### 根因③（次级）：验收命令行内注释

幂等条款写成 `!... verify_rbac.py（**二次运行仍 exit 0**）`，注释被 cmd 当命令文本执行。
纪律：**`!` 验收命令必须是纯命令，注释一律挪到独立文字判据行。**
