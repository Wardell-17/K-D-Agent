# 实验记录 048 ｜ 方案 B 端点冒烟：K3 coding 端点 `$web_search` —— 端点层否决

日期：2026-08-26 ｜ 性质：可行性冒烟（否定性结论，证据留存）

## 问题

检索分层三级预案中，"K3 联网取证写进卡片事实"这一步能否直接在编排器内完成？
即：K3 coding 订阅端点（api.kimi.com/coding）是否支持内置 `$web_search` 的完整协议闭环。

## 方法

`kd_kimi_search_probe.py`：原始 HTTP 精确控制协议，判别性提问
（"2026 年 7 月中国官方制造业 PMI"），最多 4 轮往返。

## 实测结果（2026-08-26 复跑确认）

| 步骤 | 结果 |
|---|---|
| step0：声明 `$web_search` 工具 | ✅ 端点接受，模型主动发起搜索（finish=tool_calls） |
| step0 返回内容 | `arguments` 含 `search_result.search_id` 引用 + `usage.total_tokens ≈ 7450` |
| step1：回传 tool 结果（6 个变体逐一试） | ❌ 全部 `HTTP 400 tokenization failed` |

已试变体（全灭）：官方协议原样回传（search_id 引用）、arguments 字符串化、
去 content 字段、带 name 字段、判别性回传（直接给搜索结果文本而非 search_id 引用）等。

对照：platform 端点（api.moonshot.cn）对订阅 key 返回 401（002 老教训复验）——
订阅 key 只认 coding 端点，而 coding 端点不支持 builtin 搜索的协议闭环。

## 结论

**方案 B 在端点层不可行**：coding 端点会"发起"搜索（且每次消耗约 7500 tokens），
但第二轮回传无论什么格式都 tokenization 400，无法完成闭环。
这不是参数调试问题，是端点能力边界。

附带计费线索：搜索发起即计约 7500 tokens/次，若未来端点修复，
预算上也要按"每次搜索 ≈ 一次长上下文调用"计。

## 对检索分层策略的影响（替代 047 三级预案）

```
国际/英文题：Tavily（1000/月免费档）→ Brave（新用户 $5/月额度≈1000 次，
             2026 年初起无真免费档，需注册决策）→ 诚实失败
国内/中文题：Tavily → 总控检索前移（**当前 Kimi Work 总控**：订阅内联网，
             无 API 账单、计费明确；结果写进卡片"已确认事实"，零开发量）
             → 或评估国产搜索 API（博查等，需用户决策是否注册，质量未实测）
末级：诚实失败（标注未核实，绝不静默降级到垃圾信源）
```

⚠️ 边界（exp015 实证）：DSH 自带的 DeepSeekSearchProvider 检索那次 model turn
**不进 TokenMeter 账单**（记账缺口）——未来 preset 移植到 DSH 后，
总控检索**不得**用 DSH 原生 web_search，仍走编排器自己的 driver 链。"总控前移"
仅指当前 Kimi Work 订阅侧。

要点：编排器内不再追求"自己联网"；联网取证前移到 meta-agent 总控层（DSH/Kimi Work），
编排器只消费卡片里的已确认事实——这与 meta-agent 架构分工一致，反而更干净。
